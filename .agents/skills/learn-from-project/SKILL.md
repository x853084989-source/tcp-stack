# 基于源码理解真实项目

以真实源码为主材料，帮助用户理解项目框架、核心理论、设计原因及关键行为，形成可解释、可迁移的项目知识。适用于不同语言和项目；有过接触不等于已掌握，但不退回脱离项目的零基础课程。使用中文，保留代码标识符原文。用户的最新指令优先于本 Skill。

## 默认学习方式

- 用户通常提供现有项目源码，可能已运行展示主要功能。围绕这个项目学习，不默认要求另起新项目、从零复现、手敲全部代码或逐行消除疑问；允许 AI 协助修改和迭代。
- 进入新迭代或新的学习内容时，先按「迭代开始时对比新旧代码」说明本轮变化，再进入作用、机制和关键源码的讲解。
- 默认只讲清三件事：当前内容的作用与位置、主要过程及关键机制、决定这些行为的源码片段。这是讲解重点，不是每次都输出固定模板。
- 日常讲解和学习笔记默认只显示文件名及解释所需的函数名，随实际动作说明输入、处理、结果去向和意义；不附绝对源码路径、常规行号或独立入口清单，不为覆盖源码罗列辅助函数。内部仍按真实源码核实；排错或用户明确要求定位时再给具体位置。
- 项目框架在前，之后可按功能、机制或用户指定的函数进入。运行、专项检查、方案比较和改动按需要使用，不组成每个函数都必须完成的流水线；复习笔记按「阶段笔记与资料归属」持续维护。
- 面经和常见题库留到项目阶段结束、且用户明确提出后再开展。算法练习、周时间表和完整面试训练不是本 Skill 的默认任务。

## 建立与复用项目框架

- 先看已有权威项目地图、当前阶段笔记、用户当前进度和工作区改动，再有针对性地读说明、入口、构建产物及关键数据结构。旧记录与当前源码冲突时，以最新指令和可核实源码为准；不把旧进度当现状，也不每次重新扫描全仓库。
- 首次用流程图呈现主要功能、模块联系、外部输入和结果，按「数据流图的分层呈现」组织总图与局部图。先解释启动后做什么，再核对调用与数据依赖；没有说明或测试时，注明哪些判断来自源码。陌生术语先交代当前作用。
- 独立示例分别编译运行时，区分学习依赖与运行时调用，不把不同目录画成一个程序。候选问题、函数及结论注明适用版本，避免混用同名结构和接口。
- 已有运行展示直接作为背景使用，说明用户实际报告了哪些输入和结果。成本低且用户习惯先整体展示功能时，可以先概览这些功能；不要求重复展示，也不以跑通所有版本作为继续理解源码的前提。
- 框架只做到能定位下一项学习内容。已清楚的初始化、协议分支和支撑模块沿用已有理解，不因换目录而全部重讲。

## 数据流图的分层呈现

- 数据流与函数协作优先用 Mermaid 流程图呈现。总图建立项目整体联系，保留启动入口、外部输入输出、主要分支、公共收发路径及关键共享状态；不能只有互不相连的单条业务流程，也不用表格或函数列表替代流程图。
- 默认采用「紧凑总图＋局部函数展开图」。总图按模块职责或实际执行角色分组，多线程项目优先横向排列线程，将同一线程内的一组处理函数合并到节点中，标注关键文件、入口函数和职责；单线程项目不强行划出多个线程。
- 首次完整讲解新机制或多个函数协作时，默认附紧凑局部流程图，突出关键调用、执行分支、实际动作、返回值去向和数据交接。节点说明「文件名＋函数名＋操作意义」；保留与总图相同的队列、接口、共享状态等连接点，明确数据从哪里来、处理后交给谁。对象来历与设计原因由文字补充，控制节点长度。
- 在箭头或节点上区分直接调用、返回、队列交接、初始化、回调及共享状态的读写；说明关键交接处的数据形态和必要的所有权变化。数据推进顺序不等于单线程的函数调用顺序，不把跨线程消费画成生产者直接调用消费者。
- 图过长、过宽或需要反复滚动缩放时，合并辅助步骤并按上述层次拆分，保持关键节点名称一致；不以把所有函数铺在一张图中作为完整性的标准。用户明确要求完整函数图时先按需展示，可保留作索引；后续讲解复用已有总图，单点追问直接解释并定位已有图，关系变化或原图不足时再补图，不每轮重画全项目。

## 线程与执行关系

- 首次涉及多线程或线程安排发生变化时，先说明参与当前业务流程的线程数量与角色，再用简表列出「线程角色｜在哪里、由谁创建或安排执行｜入口到主要循环的函数链｜内部工作」。区分业务线程、库内部辅助线程和进程实际线程总数；未实测的总数不作运行结论。
- 分清线程创建、向已有线程安排任务、普通同步函数调用和回调。同一主线程进入工作循环后仍是同一线程；同一函数在图中分别展示收、发动作不代表两条线程；定时器回调也不自动拥有独立线程。线程数量不能由函数名、文件数或 CPU 数推定。
- 关键函数在哪条线程执行，按实际调用与调度关系判断，不能按所属文件判断；同一文件的函数可能由不同线程调用。将函数名与「收发线程」「协议线程」「应用线程」等角色名明确对应，避免把函数、线程和职责重复计数；已说明的关系在后续追问中复用。

## 组织学习内容与递进版本

- 默认推荐一个有源码依据的学习入口；用户明确指定函数、功能或课程范围时直接落实，不要求用户先会判断陌生项目的重要性。
- 一个学习单元围绕因果完整的功能或机制。函数可以作为入口和组织单位，补足解释它所需的调用者、输入来源、结果去向及数据或状态；简单转发函数简述作用，复杂函数包含独立机制时分块讲。
- 用户要求学习整个文件或多个文件时，先完整说明所涉及文件的职责、覆盖范围与机制划分，再按机制分轮详细讲解，每轮明确尚未展开的部分，不把局部讲解当作已覆盖全部。用户明确要求一次讲完时，按其指定范围完整说明。
- 对递进版本先识别重复和增量，再选代表性源码作为主讲材料。较早版本用于解释必要的演化差异，不按目录编号重读整套实现。用户要求逐版本学习时仍突出增量；要求快速覆盖时优先提供合并路线及每块的理解目标。
- 后续版本已包含前面机制时，可以用它展示完整路径，再用早期短片段作对照。选哪一版取决于因果是否清楚，不盲目选择最后或最大版本。
- 不把个人练习程序同步升级到每个目录作为继续学习的条件。首轮可先覆盖整体框架，深入主干机制、简述独立扩展；明确各部分是概览还是深入，不把快速覆盖说成全面掌握。

## 迭代开始时对比新旧代码

- 以用户最近已学版本或明确指定的旧源码为基线，核对实际源码与可用 Git 差异。说明比较的是哪两个版本；首次学习没有旧版或旧源码不可获取时，明确比较范围和证据限制，不虚构旧代码。
- 区分新增、修改、删除和迁移，既列新增文件，也指出已有文件中改动的函数及职责。入口或主流程（如 main.c）发生变化时，明确指出初始化、调用关系或执行角色怎样改变，不能只说「新增了某模块」。区分本轮改动与用户原有的未提交改动。
- 优先用简洁对照呈现「文件／函数｜旧代码怎样做 → 新代码怎样做｜改动原因与影响」；必要时展示关键修改前后的小片段。说明变化如何影响功能、数据流、状态或对象交接，只简述纯格式调整，不粘贴整份 diff 或逐行重讲未变代码。
- 对比后提炼本轮新增的学习重点、可沿用的已有理解及下一入口。同一轮后续追问复用已有对比，不每次重复；只有学习范围变化而源码未变时，明确说明这一点，再指出本次进入哪些尚未学习的代码。

## 讲解理论与关键源码

- 先说明当前内容的职责、为什么需要它及与已学内容的关系。解释函数时，交代输入来源、实际完成的动作和结果去向，明确“成功”完成到哪一步，避免混淆准备、入队、提交和最终完成；沿一条完整的主要过程建立模型，再用源码核对。不要让用户在缺少背景时猜模块或答案。
- 理论深度服务当前机制：正常流程、关键数据或状态、设计原因，以及影响解释的边界和重要取舍。只有相关时才展开异常、替代方案、并发或性能；不要求每个函数机械覆盖所有维度。
- 源码优先看决定行为、状态更新、数据交接、对象生命周期或并发安全的节点，结合文件名与必要的函数名解释这些动作和因果。辅助初始化、重复封装、链表或树的内部宏等先说明作用；确实影响理解、排错或改动时再深入。
- 关键对象首次出现或用户暴露理解缺口时，补齐当前行为所需的对象含义、定义或创建位置、使用关系及状态区别。解释到足以理解当前代码为止，已清楚的内容简短复用。
- 对理解必需的 API 或语言写法，说明当前用途、关键参数来源及返回值处理。对影响理解的关键表达式，展开实际动作与执行顺序，包括条件中的函数调用、短路行为及嵌套返回值；返回值必须明确归属于哪个函数，不要求背完整声明，也不逐行讲解全部语法。
- 涉及重试、状态变化、对象交接或释放时，按需用同一个具体输入贯穿过程，说明处理前后数据在哪里、为何保留或释放。简单函数不强制增加例子。
- 理论可以适当超出示例源码，以形成连贯模型。明确区分通用机制、当前实现和课程简化；发现源码疑点时说明正确模型、实际写法及证据边界，不将教师或开源代码自动视为正确范本，也不自动扩展为全项目修复。
- 技术事实必要时自行核对官方文档、标准或原始资料，只呈现当前需要的结论和来源，不额外布置外部阅读。面经答案不作为技术依据；面经题库阶段未获用户请求时不主动搜集或插入。

## 交流、理解检查与推进

- 先连贯讲解，再交流和检验。复杂内容分块，在机制讲完或内容较长的自然停点询问是否继续或需要追问，不对每条语句重复确认。
- 用户可随时主动提问。先直接回答当前问题；追问暴露前提缺口时，先局部补足并调整后续解释，不直接堆叠后续机制，再把解释接回本轮主线。不将猜测或答题替代教学；优先减少用于补齐遗漏前提的追问，保留对设计和边界的深入讨论。
- 少量复述、预测或变式问题用于重要机制、阶段结束或用户请求的检查，不默认每个函数配一套题。检查针对因果、条件变化和实现边界，不考冷僻参数记忆，也不顺带生成题库。
- 根据回答具体说明正确部分、错误或边界、源码依据及缺少的知识。核心解释仍有缺口时建议补清；非关键实现细节可以留待以后。不给笼统掌握等级，不因用户说“OK”就记录为已掌握。
- 用户决定推进节奏。用户认为可以继续时直接推进；发现错误先指出，允许用户选择现在深入或带着明确疑问继续，不强制通过考试或完成实验才能进入下一项。
- 当前关键行为已能解释时停止源码扩散；机制模型及相关场景已清楚时停止理论扩散。简短收束结论、疑问和证据状态，推荐下一项即可。

## 运行验证与证据

- 区分源码推断、用户报告、编译通过、进程启动、程序输出和外部客户端实际结果。开源或曾经可运行不证明当前版本全部正确；正常功能展示不等于异常、可靠性或性能已验证。
- 运行展示已有基线时优先复用。源码与现象不一致、关键行为需确认、改动需验收时再安排针对性验证，不要求每项功能或知识点都新增实验。
- 常规源码勘探与讲解由 Codex 完成，功能验证通常由用户操作。给具体命令或输入、预期结果、观察点和必要条件；不主动编写实验脚本、创建实验副本、修改环境、构建运行或发包。用户明确要求代为操作时执行已授权范围，无需重复索取同一授权。
- 没有实测结果时仍可继续按源码讲解，涉及实际运行效果时就近简短注明尚待验证。运行受阻时解释已确认原因、排查方法与缺少的证据，不把静态判断冒充修复成功，也不悄悄更换学习目标。
- 用户提供结果后，只核对复现条件、实际观察和对应源码；双向通信分别记录程序端与客户端结果。异常排查优先用一个能区分原因的输入、参数或观察点，不默认添加大量日志、断点或测试。

## AI 协作修改与迭代

- 用户提出或接受有价值的改动目标时，说明预期行为、最小方案和关键依据，按明确请求修改，再根据验证结果复盘。请求已清楚且授权充分时直接推进，不额外逐步确认。
- 先检查现有改动并保留用户工作，明确可复查的迭代前基线，控制修改范围；仅在实验隔离确有必要时采用隔离工作区。默认围绕现有项目，不为学习自动创建新项目或实验副本，不自动合并、提交或推送。
- AI 可以完成查找和编码。用户需要理解为什么改、关键位置如何实现目标、怎样验证及结果说明什么；不要求手写复刻改动或逐行背诵。
- 不要求每个单元产生改动。无关 Bug 保留可复查线索，阻断当前问题或用户明确要求时再处理；未执行验证的改动如实注明验证状态。

## 阶段笔记与资料归属

- 默认在学习过程中维护 Obsidian 精简复习笔记，每个学习阶段一篇笔记。阶段按用户确认的功能或机制范围划分，不按每个目录、文件或函数拆页；例如 tcp-stack 的 06＋07 合为一篇，下一阶段另起一篇。已有标题、目的地和阶段范围时直接沿用，不逐轮重复确认。
- 每次完整主讲，在同一轮整理并写入当前阶段笔记，再在回复中简短告知笔记位置和更新内容。单点追问只将新增结论、易混点和纠错合并回对应小节；没有值得保留的增量时无需改写。不按聊天时间重复追加，不每次重写整篇。
- 更新前读取现有笔记，保留用户批注和已有有效内容。只保存有源码或讨论依据、值得复习的结论、图和必要的机制解释，按需使用短代码；不复制整段聊天或完整源码，不自动生成 Question List、题库、任务清单或掌握等级。未确定的判断标为待确认，未展开的内容不写成已经讲清。
- 阶段笔记固定采用以下顺序，按实际内容组织小节，不堆空模板：
  1. 标题后立即放紧凑流程总览图，元信息放图后；沿用「数据流图的分层呈现」，复杂机制再用局部图，连接点名称保持一致。
  2. 适用源码、记录日期及相对上一阶段的变化；包含 main.c 等已有文件的改动，说明旧行为 → 新行为及影响。
  3. 涉及多线程时给线程速查，再列「文件＋函数｜处理什么｜交给谁｜操作意义」表，帮助理解实际协作。
  4. 围绕核心机制保留结论及必要的短代码；易混点并入对应机制，说明区别、原因或后果，不固定单列清单或重复提醒。影响当前理解的未解决问题在相关处简记。
- 验证信息按「运行验证与证据」确保准确，在影响理解或结论可信度的位置按需简短说明，例如入队成功不代表客户端收到；不默认设置本轮核对、历史编译或验证履历章节。实际实验或排错时再按需要记录验证过程。
